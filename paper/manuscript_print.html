Abstract

Context: As Large Language Model (LLM) agents transition from conversational assistants to autonomous execution actors in digital engineering and media production projects, project management faces a critical governance gap. Multi-agent workflows frequently suffer from uncoordinated role handoffs, non-idempotent external side effects (such as duplicate platform publications following network timeouts), silent quality degradation, and confounded performance attribution.
Objective: Grounded in the Design Science Research (DSR) paradigm and stage-gate project control theory, this study designs, implements, and empirically evaluates an auditable human-in-the-loop (HITL) project governance framework and release operations system (Agentic Work Lab and PublishOps CrossCast) for multi-agent, multi-platform digital delivery.
Method: We formalize a four-layer governance architecture comprising: (1) a deterministic sole-operator and temporal scheduling gate (planRun); (2) cryptographic plan-hash locking (--confirm CURRENT_PLAN_HASH) coupled with stream-based SHA-256 media integrity and frame-level quality verification; (3) an idempotent receipt state machine that latches uncertain post-submission outcomes (UNKNOWN states) to suppress automatic retry faults across heterogeneous API and browser-automated endpoints; and (4) an independent read-back verification, in-place revision, and HITL exception handoff protocol. The framework is evaluated using longitudinal project artifacts spanning N = 69 de-identified operational event logs, N = 55 channel publication records, N = 30 cryptographically verified video delivery versions (2.21 GB), and 2,737 automated verification test cases across 126 test modules.
Results: Across 69 operational checkpoints involving multi-agent coordination (GPT/Codex, Claude, and DeepSeek under human project management), the governance gates suppressed unauthorized mutations in 68 non-write intervals while executing exactly one authorized write (0 duplicate upload replays, 0 new risk incidents). A verified autonomous heartbeat run demonstrated a 24.992 s trigger delay and 31.175 s execution duration with zero task errors. Cross-platform release evaluation across five platforms (Bilibili, YouTube, X, Douyin, and Instagram) confirmed that latching UNKNOWN states during programmatic read-back timeouts prevented duplicate publication on Douyin while preserving audit trails. Phase-level latency decomposition on Instagram (423.236 s end-to-end; 412.217 s publication command) revealed that 92.32% (380.551 s) of command duration resides in post-submission platform confirmation wait, identifying the primary vulnerability window for non-idempotent agent retries.
Conclusions: Effective project management of agentic workflows requires shifting from prompt-level persuasion to deterministic stage-gate invariants, cryptographic artifact locking, and idempotent state-machine recovery. All source code, schemas, and de-identified empirical datasets are publicly archived to establish a reproducible benchmark for agentic project governance.

1. Introduction

The rapid maturation of Large Language Models (LLMs) and autonomous tool-using agents has initiated a structural transformation in project management, software engineering, and digital operations (Holzmann et al., 2022; Müller et al., 2024; Wang et al., 2024). Unlike traditional automation scripts that execute fixed, deterministic subroutines within narrow integration boundaries, modern agentic workflows deploy heterogeneous foundation models—such as reasoning-oriented coding agents, interface construction agents, and scheduled monitoring agents—to collaborate on complex, multi-stage project deliverables (Wu et al., 2024; Hong et al., 2024; Qian et al., 2024). In digital media production, software release engineering, and commercial outreach operations, these multi-agent topologies promise substantial reductions in manual coordination overhead and turnaround time (Raisch & Krakowski, 2021; Berente et al., 2021).

However, deploying autonomous or semi-autonomous AI agents into real-world production environments exposes severe project governance vulnerabilities that classical project management methodologies (PMI, 2021; Kerzner, 2022) and conversational multi-agent frameworks were not designed to address. From a systems control and project management perspective, four fundamental failure modes emerge when LLM agents interact with shared repositories and external production platforms:

  1. Multi-Agent Handoff Drift and Role Ambiguity: When multiple specialized models (e.g., GPT/Codex for script synthesis, programmable video generation, and backend verification; Claude for CLI interface construction and layout adaptation; and DeepSeek for scheduled operational monitoring) operate asynchronously on shared project state, context boundaries frequently degrade. Without formal ownership locks and explicit acceptance gates, an operational agent waking up on a cron schedule may re-execute a task already claimed by another instance, overwrite human-approved revisions, or act upon stale schedule checklists (Whyte et al., 2016; Qian et al., 2024).
  2. Non-Idempotent External Side Effects under Platform Uncertainty: Real-world release operations across heterogeneous digital platforms (such as Bilibili, YouTube, X, Douyin, and Instagram) rely on a complex mixture of official OAuth REST APIs and stateful browser sessions. Network interruptions, asynchronous platform transcoding queues, CAPTCHA verification challenges, or DOM read-back timeouts frequently leave a submission in an indeterminate (UNKNOWN) state (Schneider, 1990; Kleppmann, 2017). Naive agentic retry loops interpret a missing confirmation receipt as a failed upload and automatically re-click submission controls, resulting in duplicate public posts, corrupted playlist ordering, or account rate-limiting penalties.
  3. Opaque Quality Degradation in Generative Deliverables: One-shot generative media and text pipelines frequently introduce localized technical defects—such as single-frame luminance flashes before transitions, audio-visual synchronization drift, clipped floating-point audio tracks, or mobile overlay cropping—that pass superficial completion checks. Without code-driven editable intermediate representations and deterministic signal verification gates, repairing a localized defect requires regenerating the entire deliverable, destroying previously validated segments.
  4. Epistemic Confounding in Project Performance Evaluation: In both industry white papers and academic literature, the adoption of AI workflows is frequently accompanied by unverified claims of labour savings or audience growth (Raisch & Krakowski, 2021). When comparing historical human-led project outputs against newly launched AI-assisted series, differences in artifact exposure age (e.g., years of cumulative platform traffic versus days), topic selection, and platform recommendation dynamics severely confound naive metric comparisons. Furthermore, treating generated draft volume as equivalent to verified, production-ready delivery obscures the substantial human review and rework required to achieve release acceptance.

To address these challenges, this study adopts the Design Science Research (DSR) methodology (Hevner et al., 2004; Peffers et al., 2007; Gregor & Hevner, 2013; Venable et al., 2016) to conceptualize, architect, implement, and empirically evaluate a comprehensive human-in-the-loop (HITL) project governance framework and release operations system: Agentic Work Lab and its standalone multi-platform release engine PublishOps CrossCast (vpub). Rather than treating AI governance as an informal prompt-engineering exercise, we formulate multi-agent project delivery as a verifiable stage-gate control system (Cooper, 1990; Bianchi et al., 2022) backed by cryptographic artifact locking, frame-accurate quality gates, and fault-tolerant state-machine transitions.

Specifically, this paper investigates the following three research questions (RQs):

  • RQ1 (Governance Architecture & Handoff Control): How can stage-gate project management principles be formalized into deterministic software invariants to govern multi-model handoffs (GPT/Codex, Claude, and DeepSeek) and prevent unauthorized or duplicate autonomous actions?
  • RQ2 (Idempotent Release Engineering & Fault Recovery): How can a persistent receipt state machine coordinate multi-platform digital releases, in-place revisions, and authorized deletions across hybrid API and browser-automated channels when post-submission verification encounters timeouts or human authentication barriers?
  • RQ3 (Empirical Latency, Quality & Epistemic Validation): What are the empirical operational characteristics, latency bottlenecks, multi-modal defect repair patterns, and methodological boundaries observed when deploying this governance architecture across longitudinal multi-platform production workflows?

The primary contributions of this work are fivefold:

  1. A Four-Layer Agentic Project Governance Framework: We synthesize stage-gate project control (Cooper, 1990) and human-centered automation theory (Parasuraman et al., 2000; Shneiderman, 2020) into four enforceable governance layers: (i) Sole-Operator and Temporal Scheduling Gate, (ii) Cryptographic Plan-Hash and Multi-Modal Artifact Integrity Gate, (iii) Idempotent Receipt State Machine with UNKNOWN-State Suppression, and (iv) Independent Read-Back, In-Place Revision, and HITL Verification Handoff.
  2. Formal Algorithms for State-Locked Release Operations: We present three formal algorithms governing deterministic job planning (Algorithm 1), idempotent publication with pre-commit receipt latching (Algorithm 2), and identity-bound in-place metadata revision and durable-consent deletion (Algorithm 3).
  3. Open-Source Reference Implementation (PublishOps CrossCast): We detail the engineering architecture and longitudinal evolution (from v0.2.2 through v0.16.0 and PR #30, commit 75b7abc) of PublishOps CrossCast, comprising 123 Python source modules (27,095 lines of code) and 126 automated test modules (37,155 lines of test code across 2,737 test functions), alongside zero-dependency Node.js verification scripts in Agentic Work Lab.
  4. Longitudinal Empirical Trace and Latency Bottleneck Discovery: We evaluate the system across 69 de-identified operational event records, 30 SHA-256 verified video delivery versions (2.21 GB), frame-level defect scans across 13,034 frames, and live cross-platform publication across five major platforms (Bilibili, YouTube, X, Douyin, and Instagram). Our phase-by-phase timing decomposition demonstrates that post-submission platform confirmation accounts for 92.32% (380.551 s out of 412.217 s) of browser-mediated publication latency, empirically proving why persistent pre-wait commit latching is indispensable.
  5. Methodological Protocol for Auditable AI Project Reporting: We establish and demonstrate a strict reporting protocol that separates primary observational receipts from causal inferences, preventing survivorship bias and exposure-age confounding when evaluating human-led (n = 45) versus AI-assisted (n = 10) project cohorts.

2. Related Work and Theoretical Background

2.1 Project Management Governance and Stage-Gate Control in the AI Era

Classical project management theory emphasizes structured control mechanisms—such as Work Breakdown Structures (WBS), configuration management, and Stage-Gate reviews—to manage technical uncertainty and enforce accountability across project phases (Cooper, 1990; Whyte et al., 2016; PMI, 2021; Kerzner, 2022). In Cooper's Stage-Gate model and subsequent hybrid agile–stage-gate frameworks (Bianchi et al., 2022), iterative execution within a development stage is separated from downstream commitment by formal decision gates. Each gate comprises predefined deliverables, explicit quality criteria, and an authoritative gatekeeper who decides whether to proceed, recycle for rework, hold, or terminate the activity.

Recent scholarship in project management has begun examining how artificial intelligence alters project governance, decision-making authority, and human–machine agency (Holzmann et al., 2022; Müller et al., 2024). Raisch & Krakowski (2021) highlight the fundamental tension between automation and augmentation in management: over-automation (removing human judgment from critical control loops) leads to systemic drift and brittle failure modes under novel edge cases, whereas isolated augmentation fails to capture end-to-end operational scalability. Similarly, foundational work in human factors by Parasuraman et al. (2000) and Shneiderman (2020) demonstrates that high-reliability socio-technical systems must combine high automation capability with high human control through transparent audit trails, explicit pre-authorization, and graceful exception handoffs. Despite these theoretical advances, existing project management literature largely relies on conceptual typologies or expert Delphi surveys (Holzmann et al., 2022); there remains a critical gap in translating stage-gate governance into concrete, software-enforced invariants for live, multi-model AI agents.

2.2 Multi-Agent LLM Workflows and Coordination Vulnerabilities

The emergence of reasoning-and-acting paradigms such as ReAct (Yao et al., 2023) and Reflexion (Shinn et al., 2023) has catalyzed multi-agent collaborative frameworks including AutoGen (Wu et al., 2024), MetaGPT (Hong et al., 2024), and ChatDev (Qian et al., 2024). MetaGPT encodes Standardized Operating Procedures (SOPs) into role-specific prompts (e.g., product manager, architect, engineer, QA), while ChatDev structures software development as a sequential chat chain. While effective on self-contained coding benchmarks (Wang et al., 2024), deploying conversational multi-agent systems into continuous, multi-platform production operations exposes severe limitations:

  • Absence of Cross-Process Execution Locks: Prompt-based SOPs do not prevent two agent sessions (e.g., an interactive coding session and a background scheduled heartbeat) from concurrently mutating the same local browser profile or checklist file.
  • Lack of Cryptographic Plan-to-Artifact Binding: In conversational handoffs, an agent may approve a text summary while the underlying binary artifact on disk remains an older, unpatched version or suffers from silent read corruption.
  • Unbounded Retry Loops on External Timeouts: Standard agent tool-calling loops treat HTTP timeouts or DOM selector failures as transient errors and automatically re-invoke the tool, causing catastrophic duplicate publications when the external platform actually accepted the initial submission.

2.3 DevOps, Release Engineering, and Idempotent State Machines

In software engineering, Continuous Integration and Continuous Delivery (CI/CD) pipelines mitigate deployment risk through automated build verification, immutable artifact digests, and staged rollouts (Humble & Farley, 2010; Bass et al., 2015; Adams & McIntosh, 2016; Shahin et al., 2017; Leite et al., 2019). A cornerstone of fault-tolerant distributed systems and transaction processing is idempotency—the guarantee that repeating an operation or recovering from an interrupted request does not produce duplicate side effects (Schneider, 1990; Gray & Reuter, 1992; Kleppmann, 2017). 3. Research Methodology

3.1 Design Science Research (DSR) Framework

We structure this investigation following the six-step Design Science Research Methodology (DSRM) established by Peffers et al. (2007) and the evaluation guidelines of Hevner et al. (2004), Gregor & Hevner (2013), and Venable et al. (2016):

  1. Problem Identification and Motivation: Uncontrolled multi-agent handoffs, duplicate external writes during uncertain platform states, localized defects in generative media, and confounded efficiency claims in AI-assisted project delivery (Section 1).
  2. Definition of Solution Objectives: Establish a deterministic governance architecture that enforces sole-operator scheduling, cryptographic plan-to-artifact binding, zero-duplicate submission under UNKNOWN states, surgical frame/audio defect repair, and strict separation of observational evidence from causal inference.
  3. Design and Development: Formulation of the four-layer governance model, mathematical invariants, and formal algorithms (Section 4), realized through two coupled open-source artifacts: Agentic Work Lab and PublishOps CrossCast (Section 5).
  4. Longitudinal Demonstration: Deployment of the artifacts across an authentic multi-series digital media production and cross-platform publishing laboratory spanning two episodic series (GPT Duty Log Ep 01–06 and Whale Girl Shift Log Ep 01–07), standalone experimental studies, and the cross-platform short film I Watched It For You (v3).
  5. Multi-Method Empirical Evaluation: Following the Framework for Evaluation in Design Science (FEDS; Venable et al., 2016), we combine naturalistic trace evaluation (N = 69 operational events, 5-platform live release, and N = 55 cohort records) with rigorous offline fault-injection verification (2,737 unit/integration tests in CrossCast and 10 workflow gate tests in Agentic Work Lab) (Section 6).
  6. Archival Communication: Publication of all source code, SHA-256 verified media deliverables (N = 30 versions, 2.21 GB), and machine-readable JSON/CSV receipts to enable independent reproduction.

3.2 Epistemic Hygiene and Evidence Classification Protocol

A central methodological contribution of this study is the enforcement of an explicit epistemic hygiene protocol across all project documentation and data exports (Runeson & Höst, 2009). For every research topic and operational update, the laboratory records four distinct elements: (i) the original claim, (ii) visible primary evidence, (iii) an independent verification test, and (iv) applicable methodological limits. Specifically:

  • Separation of Observation and Causal Inference: Direct platform observations (e.g., lifetime views, 24-hour completion rates, or command durations) are stored with exact sampling timestamps and provenance notes. Causal inferences (e.g., asserting that an AI editing technique increased algorithmic recommendations) are rejected unless backed by controlled, age- and topic-matched experiments.
  • Granular State Differentiation: The system distinguishes between local preparation, dry-run rehearsal, sign-in preflight, submission execution, platform review queues, and verified public visibility. UI observations and API verifications occupy separate state fields; an unverified or timed-out read-back is recorded as UNKNOWN rather than coerced into success or failure.
  • Immutable Snapshot Preservation: Repeated data collections are archived as separate observations (e.g., retaining the 2026-10-28 afternoon 52-record snapshot separately from the evening 55-record snapshot and subsequent daily updates from 29 October to 3 November) rather than overwriting historical files.
  • Explicit Tagging of Unexecuted Plans: Pre-registered experimental designs (such as the blinded identical-task multi-model merchant evaluation) and unmeasured optimizations (such as live concurrent-publication wall-clock speedup) are explicitly marked as unrun plans until live empirical receipts are generated.

4.2 Layer 1: Deterministic Sole-Operator and Temporal Scheduling Gate

To prevent race conditions and unauthorized autonomous execution during scheduled heartbeats, Layer 1 enforces a pure offline decision function Gplan before any network or platform adapter is invoked. Let S = (e, o, fstop, frun, tnow, J) denote the operational context tuple, where e is the requesting executor identifier, o is the registered instance owner, fstop ∈ {true, false} is the emergency halt flag, frun ∈ {true, false} indicates whether an execution lock is active, tnow ∈ ℝ+ is the current epoch timestamp, and J = {j1, …, jm} is the set of candidate jobs.

Gplan(S) = [ (skip, not_owner, ∅) if e = ∅ ∨ e ≠ o;   (skip, stop_flag, ∅) if fstop = true;   (skip, already_running, ∅) if frun = true;   (plan_only, checked, D) if D ≠ ∅;   (no_work_due, checked, ∅) otherwise ]
(1)

where the due set D is strictly filtered as:

D = { idk  |  jk ∈ J  ∧  donek = false  ∧  authk = true  ∧  tdue,k ≤ tnow }
(2)

Furthermore, for any automated run record R = (trig, status, fmanual, tstart, tend, Eerr), post-execution verification Vsched(R) holds if and only if:

Vsched(R) ⇔ (trig = automation_heartbeat_scheduled) ∧ (status = VERIFIED_AUTOMATIC_RUN_COMPLETED) ∧ (fmanual = false) ∧ (0 < tstart ≤ tend < ∞) ∧ (|Eerr| = 0)
(3)
Algorithm 1: Deterministic Sole-Operator & Temporal Scheduling Gate (planRun & verifyScheduledRun)
Input: Context tuple S = (e, o, fstop, frun, tnow, J); Run trace record R
Output: Gate decision tuple (decision, reason, D) and boolean verification result v
1:  tcur ← ParseEpoch(tnow)
2:  if ¬IsFinite(tcur) then throw Error("Invalid current time")
3:  if e = ∅ ∨ e ≠ o then return ("skip", "not_owner", ∅)
4:  if fstop = true then return ("skip", "stop_flag", ∅)
5:  if frun = true then return ("skip", "already_running", ∅)
6:  Iseen ← ∅;  D ← []
7:  for each job jk = (idk, tdue,k, authk, donek) ∈ J do
8:     if idk = ∅ ∨ idk ∈ Iseen then throw Error("Missing or duplicate job id")
9:     Iseen ← Iseen ∪ {idk}
10:    if donek = true ∨ authk ≠ true then continue
11:    tat ← ParseEpoch(tdue,k)
12:    if ¬IsFinite(tat) then throw Error("Invalid due time for " + id_k)
13:    if tat ≤ tcur then Append(D, idk)
14: end for
15: decision ← (|D| > 0) ? "plan_only" : "no_work_due"
16: return (decision, "checked", D)

As formalized in Algorithm 1, planRun operates as a strict, side-effect-free admission filter. First, it validates temporal integrity by parsing the reference clock tnow into a finite epoch value (lines 1–2). Next, it enforces three ordered circuit-breaker checks: executor ownership verification (line 3), emergency stop-flag inspection (line 4), and active-execution lock detection (line 5). Only when all three preconditions pass does the algorithm iterate over the candidate job set J, maintaining a seen-identifier set Iseen to immediately reject malformed or duplicate job identifiers (lines 6–9). Tasks that are already completed (done = true) or lack explicit human pre-authorization (auth ≠ true) are deterministically bypassed (line 10). Crucially, even when eligible due tasks are identified (|D| > 0), Layer 1 returns plan_only rather than directly mutating external platforms, requiring downstream layers to validate cryptographic artifact digests and confirmation hashes before execution.

4.3 Layer 2: Cryptographic Plan-Hash Locking and Multi-Modal Artifact Verification

In multi-agent workflows, a subtle but critical vulnerability arises between plan approval and execution: an agent or background process may modify a video export, swap a cover image, or alter platform copy after the human project manager has reviewed the preview. Furthermore, large binary media deliverables (ranging from 2.5 MB to 285.8 MB in our archive) can suffer from incomplete writes, silent disk read corruption, or container-level encoding defects. Layer 2 eliminates this time-of-check to time-of-use (TOCTOU) gap by enforcing two formal invariants prior to release staging:

Governance Invariant 1 (Binary & Multi-Modal Media Integrity): Let M = {m1, …, mK} be the release manifest where each entry mi = (fnamei, Bi, Hi) specifies a basename-sanitized file, exact byte length Bi, and expected SHA-256 digest Hi. An artifact fi passes verification iff basename(fnamei) = fnamei ∧ size(fi) = Bi ∧ SHA256(fi) = Hi ∧ DecodeErrors(fi) = 0.
Governance Invariant 2 (Plan-Hash Confirmation Binding): Before invoking any platform write via vpub publish, a canonical release plan P—encapsulating target platforms, account identifiers, video SHA-256 digest, cover SHA-256 digest, aspect ratio, visibility mode, and platform-specific captions—is serialized and hashed as H(P) = SHA256(CanonicalJSON(P)). Execution is rejected unless the invoking command supplies an explicit confirmation token --confirm Huser such that Huser = H(P).

To avoid memory exhaustion when verifying multi-hundred-megabyte video deliverables, both check-delivery.mjs (in Node.js) and vpub (in Python) compute SHA-256 digests using chunked read streams rather than buffering entire files into memory, and sanitize all manifest file paths via path.basename to prevent directory traversal. Beyond cryptographic integrity, Layer 2 enforces domain-specific multi-modal quality gates: every video candidate must pass a full FFmpeg stream decode with zero errors, loudness normalization checks (targeting −15.97 to −17.5 LUFS with zero clipped samples), and automated low-resolution (320×180) frame-by-frame luminance and difference scans to detect single-frame ABA flashes, black-frame dropouts, or shot leakage across edit cuts.

4.4 Layer 3: Idempotent Receipt State Machine and UNKNOWN-State Suppression

To answer RQ2, we model cross-platform publication in PublishOps CrossCast as a persistent, six-state finite state machine backed by cross-process OS locks (process_lock.py) and durable local receipt journals (Figure 2 and Algorithm 2). Let Σ = {PLANNED, PREFLIGHT_OK, MEDIA_STAGED, SUBMITTED_WAIT, UNKNOWN_LATCHED, SUBMISSION_VERIFIED} denote the state space for a target platform p. Each publication attempt maintains an atomic receipt tuple Rp = (key, acctp, Hmedia, Hmeta, fsubmit, σp, widp, τlog), where fsubmit ∈ {true, false} is the persistent final-commit latch.

Input: Release plan P, confirmation token Huser, target platform p, receipt journal Rp
Output: Updated persistent receipt Rp = (key, acctp, Hmedia, Hmeta, fsubmit, σp, widp, τlog)
1:  if Huser ≠ SHA256(CanonicalJSON(P)) then abort PLAN_HASH_MISMATCH
2:  AcquireProcessLock(p, acctp)  // Recovers stale lock only if OS PID is confirmed terminated
3:  if Rp.fsubmit = true then
4:     return ReconcileExistingReceipt(Rp)  // Strictly blocks duplicate submission if already latched
5:  end if
6:  VerifyMediaStreamSHA256(P.media_file, P.expected_bytes, P.Hmedia)
7:  session ← AttachPipeBrowserOrOAuthSession(p, acctp)
8:  StageMediaWithOffsetRecovery(session, P.media_file, P.cover_file, P.caption)
9:  Rp.fsubmit ← true;  Rp.σp ← SUBMITTED_WAIT;  PersistAtomically(Rp)
10: DispatchSingleFinalCommit(session)  // Single Share / Post / Save click
11: outcome ← AwaitPlatformConfirmationAndReadBack(session, P.expected_identity)
12: if outcome.verified = true then
13:    Rp.σp ← SUBMISSION_VERIFIED;  Rp.widp ← outcome.work_id
14: else
15:    Rp.σp ← UNKNOWN_LATCHED  // Never re-clicks submit; awaits vpub verify or HITL inspection
16: end if
17: PersistAtomically(Rp);  ReleaseProcessLock(p, acctp);  return Rp

The core fault-tolerance property of Algorithm 2 lies in the strict ordering between receipt latching (line 9) and external commit dispatch (line 10). During preflight and media byte staging (States 1–3, lines 6–8), no public post exists on the target platform; if a network drop occurs during chunked upload, StageMediaWithOffsetRecovery safely resumes byte transfer from the last acknowledged offset or re-attaches to the existing studio draft. However, immediately before clicking the final platform commit button (e.g., Instagram Share, YouTube Studio Save, or Douyin Publish), the state machine sets Rp.fsubmit ← true and flushes the receipt atomically to disk (line 9). If the subsequent confirmation wait or read-back verification (line 11) times out or encounters a platform authentication challenge, the receipt transitions to UNKNOWN_LATCHED (line 15). Any subsequent invocation of vpub publish detects Rp.fsubmit = true at line 3 and routes execution to ReconcileExistingReceipt (vpub verify) rather than re-submitting the media file, thereby guaranteeing zero duplicate publications under arbitrary post-commit network or UI faults.

4.5 Layer 4: Identity-Bound In-Place Revision and Durable-Consent Deletion

Beyond initial publication, day-to-day channel operations require revising captions, updating covers, assigning chapters, and occasionally deleting test works. Naive automation agents often implement "edit" by deleting and re-uploading a post, or execute deletions without verifying that the target item matches the intended work identity. Layer 4 enforces a strict identity-bound revision and deletion protocol (Algorithm 3), implemented across PRs #20, #21, #25, #29, and #30.

Algorithm 3: Identity-Bound In-Place Revision & Durable-Consent Single-Work Deletion (vpub edit & vpub delete)
Input: Receipt key K, patch specification ΔP (or delete consent token Cdel), mode ∈ {VERIFY_ONLY, APPLY_EDIT, DELETE_WORK}
Output: Reconciled receipt state σp and audit log entry
1:  Rp ← LoadReceipt(K);  VerifyAccountOwnership(session, Rp.acctp, ΔP.expected_identity)
2:  if mode ∈ {VERIFY_ONLY, APPLY_EDIT} then
3:     live_meta ← ReadEditorNativeMetadata(session, Rp.widp)  // Ignores page translations & comments
4:     if live_meta == ΔP.target_meta then return NO_SAVE_REQUIRED_MATCHED
5:     if mode = VERIFY_ONLY then return EDIT_MISMATCH_DETECTED
6:     if p = X ∧ ¬ExposesNativeEditControl(session, Rp.widp) then
7:        abort MISSING_EDIT_ACCESS_NO_DELETE_OR_REPOST  // Never deletes or reposts as fallback
8:     end if
9:     ApplyInPlaceMutation(session, Rp.widp, ΔP)  // Preserves video bytes and visibility
10:    ReopenEditorAndVerifyReadBack(session, Rp.widp, ΔP.target_meta)
11: else if mode = DELETE_WORK then
12:    VerifyDurableConsentToken(Cdel, Rp.widp, Rp.Hmedia)
13:    ExecuteSingleWorkDeletion(session, Rp.widp)
14:    RefreshCatalogAndConfirmAbsence(session, Rp.widp)  // Verifies work is absent & neighbors intact
15: end if

Algorithm 3 introduces three critical safety guarantees for post-publication lifecycle management. First, before reading or mutating any remote item, VerifyAccountOwnership (line 1) validates that the active browser or API session matches expected_identity, preventing cross-account contamination. Second, in VERIFY_ONLY or APPLY_EDIT mode, the adapter inspects the native editor fields directly (ignoring browser-injected page translations or user comment text, line 3); if a platform account lacks native edit capability (such as a standard X post without edit access, lines 6–8), the algorithm aborts with MISSING_EDIT_ACCESS_NO_DELETE_OR_REPOST rather than destructively deleting and re-uploading the post. Third, when executing an authorized single-work deletion (DELETE_WORK, lines 11–14), the system requires a durable consent token bound to the specific work ID and media hash, waits for deletion control readiness (PR #30), and refreshes the creator catalog to verify both that the target work is absent and that neighboring works remain intact (PR #29).

7. Discussion

7.1 Theoretical Implications for Project Management and Human–AI Governance

Our findings contribute to the emerging theory of AI-augmented project management (Holzmann et al., 2022; Müller et al., 2024; Raisch & Krakowski, 2021) in three fundamental ways. First, whereas prior multi-agent frameworks (Wu et al., 2024; Hong et al., 2024; Qian et al., 2024) rely primarily on natural-language role prompts to coordinate task handoffs, our empirical trace shows that safe delegation in continuous operations requires externalizing stage-gate controls into deterministic code invariants (planRun, OS process locks, and --confirm CURRENT_PLAN_HASH). This bridges classical project configuration management (Whyte et al., 2016; Cooper, 1990) with modern agentic systems engineering. Second, in human–automation interaction theory (Parasuraman et al., 2000; Shneiderman, 2020), automation authority must be state-dependent: agents can operate with high autonomy during preflight verification and byte staging (States 1–3), but must immediately surrender retry authority to a conservative latch (UNKNOWN_LATCHED, State 5a) once an external commit flag is set. Third, by embedding provenance tracking, SHA-256 artifact manifests, and non-causal limitation tags directly into the reporting pipeline, Agentic Work Lab establishes epistemic governance as a first-class project management deliverable.

7.2 Managerial and Engineering Lessons Learned

  • Measure the Wait Before Optimizing Concurrency: Because 92.32% of live browser-mediated publication time occurs inside platform confirmation waits after submission (Table 7), optimizing local script startup yields negligible end-to-end speedup; engineering effort should focus on safe session isolation and bounded two-slot cross-platform concurrency (Figure 4).
  • Design Editable Intermediate Representations: Decomposing deliverables into code-driven timelines, separate audio tracks, and structured JSON patches allows human project managers to enforce surgical revisions (Table 8) without discarding validated upstream work.
  • Preserve Original State on Verification Interruptions: When platform security challenges or missing edit permissions occur, tools must never automatically delete, repost, or overwrite existing works.

7.3 Threats to Validity and Limitations

Consistent with software engineering case study guidelines (Runeson & Höst, 2009), we explicitly document the boundaries of this study: (1) Internal Validity: The Instagram latency decomposition (412.217 s) and the verified DeepSeek scheduled run (31.175 s) represent exact instrumented single-run observations (N = 1 each) rather than multi-trial statistical benchmarks, and client-side measurements cannot separate upload transfer from server-side transcoding during the 380.551 s confirmation wait. Furthermore, an intermittent local file-read hash discrepancy observed once prior to archiving I Watched It For You v3 was resolved on subsequent reads, but its underlying OS/storage root cause was not over-claimed as repaired. (2) Construct Validity: The pre-registered blinded identical-task multi-model merchant evaluation (comparing GPT and DeepSeek on identical prompts with token-cost logging) remains an unexecuted plan and is not claimed as an empirical result here. (3) External Validity: Empirical records derive from a single creator/engineering laboratory across five platforms (with TikTok integration suspended due to regional authentication constraints).

8. Conclusion and Future Work

This paper presented a Design Science study addressing how to govern human–AI collaborative project workflows in multi-platform digital delivery. By architecting and evaluating Agentic Work Lab and PublishOps CrossCast, we demonstrated that reliable multi-agent operations require combining clear role handoff boundaries (across human project management, GPT/Codex, Claude, and DeepSeek) with a four-layer deterministic governance framework: (1) sole-operator and temporal scheduling gates, (2) cryptographic plan-hash and multi-modal media verification, (3) an idempotent receipt state machine that latches UNKNOWN post-submission states to eliminate duplicate retries, and (4) independent read-back, identity-bound in-place revision, and human-in-the-loop verification handoffs. Empirical evidence across 69 operational events, 30 SHA-256 verified video versions (2.21 GB), 2,747 automated tests, and five live publishing platforms confirms that the architecture prevents unauthorized writes and duplicate publications while maintaining a transparent, reproducible audit trail.
