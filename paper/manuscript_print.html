Abstract

Context: When large language model (LLM) agents move from conversation to execution, project governance must control actions on external platforms that cannot be undone. An uncertain submission that is retried can be published twice, and descriptive metrics are easily reported as evidence of AI-driven gains.
Objective: Following Design Science Research (DSR) and stage-gate project control theory, we design and evaluate a human-in-the-loop (HITL) governance framework for multi-agent, multi-platform digital delivery, implemented in two open-source artifacts, Agentic Work Lab and PublishOps CrossCast.
Method: The framework has four layers: (1) a deterministic owner, stop-flag and due-time gate (planRun); (2) binding of each release command to the SHA-256 digest of the reviewed plan, with SHA-256 media checks; (3) a receipt state machine that records an UNKNOWN state before the single final submission and never re-submits automatically; and (4) independent read-back with escalation to a person. We evaluate it in a nine-day field deployment (26 October–3 November 2026) in one creator–engineering laboratory, using a 69-record operational journal, a scheduled heartbeat trace, a five-platform release of one film, 2,737 offline test functions, 30 SHA-256-recorded video versions (2.21 GB) and a 55-record channel snapshot.
Results: The journal records one platform write and no replayed upload. The heartbeat started 24.992 s late and ran 31.175 s without task errors. When Douyin's read-back timed out, the receipt stayed UNKNOWN, nothing was re-submitted, and the owner confirmed the work by phone. In one instrumented Instagram run, 380.551 s of the 412.217 s publish command (92.32%) was the wait after the single Share, spanning transfer, processing and confirmation.
Conclusions: Here, agentic delivery was governed by deterministic gates, content-bound approvals and at-most-once submission with human reconciliation rather than by prompt instructions. The evidence is single-case and descriptive; code, data and a script that recomputes every reported figure are public.

1. Introduction

The rapid maturation of Large Language Models (LLMs) and tool-using agents is changing how projects in software engineering and digital operations are run (Holzmann et al., 2022; Müller et al., 2024; Wang et al., 2024). Unlike automation scripts that execute fixed subroutines within narrow integration boundaries, agentic workflows deploy heterogeneous foundation models—reasoning-oriented coding agents, interface construction agents and scheduled monitoring agents—to collaborate on multi-stage deliverables (Wu et al., 2024; Hong et al., 2024; Qian et al., 2024). In digital media production, release engineering and outreach operations, such multi-agent arrangements promise less manual coordination and shorter turnaround (Raisch & Krakowski, 2021; Berente et al., 2021).

Deploying autonomous or semi-autonomous agents into production, however, exposes governance problems that classical project management methods (PMI, 2021; Kerzner, 2022) and conversational multi-agent frameworks were not designed to address. Four failure modes can arise when LLM agents act on shared repositories and external platforms:

  1. Multi-Agent Handoff Drift and Role Ambiguity: When several specialized models (here, GPT/Codex for scripts, code-driven video and backend verification; Claude for interface construction; and DeepSeek for scheduled monitoring) work asynchronously on shared project state, context boundaries can degrade. Without ownership locks and explicit acceptance gates, an agent woken by a schedule may repeat a task another instance has claimed, overwrite approved revisions or act on a stale checklist (Whyte et al., 2016; Qian et al., 2024).
  2. Non-Idempotent External Side Effects under Platform Uncertainty: Release operations across Bilibili, YouTube, X, Douyin and Instagram mix official APIs with stateful browser sessions. Network interruptions, transcoding queues, verification challenges or read-back timeouts can leave a submission in an indeterminate (UNKNOWN) state (Schneider, 1990; Kleppmann, 2017). Unlike payment and cloud APIs, these web submission flows offer no idempotency key that would let the platform discard a duplicate (Helland, 2012), so a retry loop that reads a missing confirmation as failure may publish twice, disturb playlist order or trigger rate limits.
  3. Opaque Quality Degradation in Generative Deliverables: One-shot generative pipelines can introduce localized defects—single-frame flashes before transitions, audio–video drift, clipped audio or mobile overlay cropping—that pass superficial completion checks. Without editable intermediate representations and signal-level checks, repairing one defect means regenerating the whole deliverable and discarding validated segments.
  4. Epistemic Confounding in Project Performance Evaluation: AI adoption is often reported with claims of labour savings or audience growth that the underlying data cannot support (Raisch & Krakowski, 2021). Comparing historical human-led output with a newly launched AI-assisted series confounds exposure age (years of cumulative traffic versus days), topic and platform recommendation dynamics, and counting generated drafts as delivered work hides the human review and rework that acceptance required.

To address these problems, this study adopts Design Science Research (DSR) (Hevner et al., 2004; Peffers et al., 2007; Gregor & Hevner, 2013; Venable et al., 2016) to build and evaluate a human-in-the-loop (HITL) governance framework and release operations system: Agentic Work Lab and its standalone multi-platform release engine PublishOps CrossCast (vpub). Rather than treating AI governance as prompt engineering, we formulate multi-agent delivery as a verifiable stage-gate control system (Cooper, 1990; Conforto & Amaral, 2016; Bianchi et al., 2022) backed by content digests, frame-level quality checks and fault-tolerant state transitions.

Specifically, this paper investigates three research questions (RQs):

  • RQ1 (Governance Architecture & Handoff Control): How can stage-gate project management principles be formalized into deterministic software invariants to govern multi-model handoffs (GPT/Codex, Claude and DeepSeek) and prevent unauthorized or duplicate autonomous actions?
  • RQ2 (Idempotent Release Engineering & Fault Recovery): How can a persistent receipt state machine coordinate multi-platform releases, in-place revisions and authorized deletions across API and browser-automated channels when post-submission verification meets timeouts or human authentication barriers?
  • RQ3 (Empirical Latency, Quality & Epistemic Validation): What operational characteristics, latency bottlenecks, defect-repair patterns and methodological boundaries are observed when this architecture is used in a nine-day field deployment across five platforms?

The contributions are fivefold:

  1. A Four-Layer Agentic Project Governance Framework: We synthesize stage-gate control (Cooper, 1990), configuration management (Whyte et al., 2016) and human-centered automation (Parasuraman et al., 2000; Shneiderman, 2020) with commit-protocol reasoning from distributed systems (Section 2.4) into four enforceable layers: (i) a sole-operator and temporal scheduling gate, (ii) plan-hash and media-integrity binding, (iii) an idempotent receipt state machine with UNKNOWN-state suppression, and (iv) independent read-back, in-place revision and HITL handoff.
  2. Algorithms with Stated Assumptions: Three algorithms govern job planning (Algorithm 1), publication with a receipt persisted before the final submission (Algorithm 2), and identity-bound revision and consent-bound deletion (Algorithm 3); Proposition 1 states the conditions under which automated re-submission cannot occur.
  3. Open-Source Reference Implementation: We describe the architecture and evolution of PublishOps CrossCast from v0.2.2 to commit 75b7abc (PR #30), whose test suite grew from 2,009 to 2,737 test functions between the v0.16.0 release and that commit, together with dependency-free Node.js verification scripts in Agentic Work Lab.
  4. Field Evidence and a Latency Profile: We report the system's behaviour in a 69-record operational journal, 30 SHA-256-recorded video versions (2.21 GB), a 13,034-frame defect scan, a crash-recovery check on a private upload, and a five-platform release in which one in-doubt submission was held without re-submission. In one Instagram publication, the wait after Share accounted for 92.32% of the publish command, which motivates persisting submission state before that wait.
  5. A Protocol for Auditable AI Project Reporting: We demonstrate reporting rules that keep observational receipts apart from causal inference, guarding against exposure-age confounding when human-led (n = 45) and AI-assisted (n = 10) cohorts are compared.

The study is a single-case design science evaluation: its claims concern how the mechanisms behaved and why, not how often such failures occur across projects (Section 7.4).

2. Related Work and Theoretical Background

2.1 Project Management Governance and Stage-Gate Control in the AI Era

Classical project management emphasizes structured control mechanisms—Work Breakdown Structures, configuration management and Stage-Gate reviews—to manage technical uncertainty and enforce accountability across project phases (Cooper, 1990; Whyte et al., 2016; PMI, 2021; Kerzner, 2022). In Cooper's Stage-Gate model and in hybrid agile–stage-gate frameworks (Conforto & Amaral, 2016; Bianchi et al., 2022), iterative work within a stage is separated from downstream commitment by decision gates, each with predefined deliverables, explicit criteria and a gatekeeper who decides whether to proceed, recycle, hold or stop. Project governance research separates the framework that assigns decision rights and accountability from the management of execution itself (Too & Weaver, 2014); in delivery terms, governance decides who may authorize an irreversible step, and on what evidence.

Recent scholarship examines how artificial intelligence changes project governance, decision authority and human–machine agency (Holzmann et al., 2022; Müller et al., 2024). Raisch & Krakowski (2021) describe the tension between automation and augmentation in management: removing human judgment from critical loops invites drift and brittle failure under novel cases, whereas isolated augmentation fails to scale. Work on human–automation interaction argues that reliable socio-technical systems combine high automation with high human control through transparent audit trails, explicit pre-authorization and graceful exception handoffs (Parasuraman et al., 2000; Amershi et al., 2019; Shneiderman, 2020). Much of the project management literature on AI, however, relies on conceptual typologies or expert Delphi surveys (Holzmann et al., 2022); translating stage-gate governance into software-enforced invariants for live, multi-model agents remains largely unaddressed.

2.2 Multi-Agent LLM Workflows and Coordination Vulnerabilities

Reasoning-and-acting paradigms such as ReAct (Yao et al., 2023) and Reflexion (Shinn et al., 2023) have led to multi-agent frameworks including AutoGen (Wu et al., 2024), MetaGPT (Hong et al., 2024) and ChatDev (Qian et al., 2024). MetaGPT encodes Standardized Operating Procedures into role-specific prompts (product manager, architect, engineer, QA), while ChatDev structures software development as a sequential chat chain. These frameworks perform well on self-contained coding benchmarks (Wang et al., 2024), but continuous multi-platform operations expose three gaps:

  • No Cross-Process Execution Locks: Prompt-based procedures do not prevent two agent sessions (for example, an interactive coding session and a scheduled heartbeat) from mutating the same browser profile or checklist at once.
  • No Binding of Approval to Artifact Content: In conversational handoffs, an agent may approve a text summary while the binary artifact on disk is an older, unpatched version or has been misread.
  • Unbounded Retries on External Timeouts: Tool-calling loops commonly treat timeouts or selector failures as transient errors and invoke the tool again, which duplicates a publication whenever the platform had in fact accepted the first submission.

2.3 DevOps, Release Engineering, and Idempotent State Machines

In software engineering, Continuous Integration and Continuous Delivery (CI/CD) pipelines reduce deployment risk through automated build verification, immutable artifact digests and staged rollouts (Humble & Farley, 2010; Bass et al., 2015; Adams & McIntosh, 2016; Shahin et al., 2017; Leite et al., 2019). A cornerstone of fault-tolerant distributed systems and transaction processing is idempotency: repeating an operation, or recovering from an interrupted request, must not produce duplicate side effects (Schneider, 1990; Gray & Reuter, 1992; Kleppmann, 2017). Payment and cloud APIs commonly accept a client-chosen idempotency key so that the server can discard duplicates (Helland, 2012); browser-driven submission to consumer platforms offers no such key, so the client alone must decide whether a second attempt is safe. 2.4 Synthesis: Reading Stage-Gate Control as a Commit Protocol

We read the two literatures together through one observation: a stage gate and a distributed commit protocol solve the same problem, namely how to make an irreversible step happen at most once, on the right object and under the right authority, when parts of the system may fail or disagree. The last row of Table 1 is the resulting design; the correspondence below states it as five design propositions that Section 4 implements and Section 6 examines.

  • Gatekeeping as admission control. A stage gate admits work only when its owner, state and criteria allow (Cooper, 1990; Too & Weaver, 2014). In software, the same decision becomes a pure function of the operating context that returns skip, no work due or a plan, never an action (Layer 1).
  • Configuration baselines as content addresses. Configuration management fixes a reviewed baseline so that what is delivered equals what was approved (Whyte et al., 2016). Hashing the reviewed plan and the media, and requiring that digest to run the command, turns approval into a binding on content rather than on a description of it (Layer 2).
  • The go decision as an at-most-once commit. Where the receiving platform cannot discard duplicates, exactly-once submission is out of the client's reach; the client can only choose between at-least-once (retry) and at-most-once (never retry) behaviour (Helland, 2012; Kleppmann, 2017). Recording the intent to submit durably before acting, as a write-ahead log does (Gray & Reuter, 1992), selects at-most-once and makes every uncertain outcome visible (Layer 3).
  • Post-gate review as an end-to-end check. Only the endpoint can confirm that an effect occurred (Saltzer et al., 1984); a local log shows only that a command was sent. Read-back from the platform is therefore the evidence that closes a gate (Layer 4).
  • Escalation as resolution of in-doubt transactions. In two-phase commit, a participant that loses contact after voting is in doubt and cannot decide alone (Gray & Reuter, 1992). An UNKNOWN receipt is the same state, and resolving it is a human decision—which also leaves people with exactly the residual cases automation cannot settle (Bainbridge, 1983). Compensation by deleting and reposting, the usual saga remedy (Garcia-Molina & Salem, 1987), is unsafe here because a public post carries replies, an identifier and reach that a repost cannot restore.

3. Research Methodology

3.1 Design Science Research (DSR) Framework

We follow the six-step Design Science Research Methodology of Peffers et al. (2007) and the evaluation guidance of Hevner et al. (2004), Gregor & Hevner (2013) and Venable et al. (2016):

  1. Problem Identification and Motivation: Uncontrolled multi-agent handoffs, duplicate external writes during uncertain platform states, localized defects in generative media, and confounded efficiency claims in AI-assisted delivery (Section 1).
  2. Definition of Solution Objectives: A deterministic governance architecture that enforces sole-operator scheduling, binds approvals to artifact content, never re-submits automatically once a final submission may have occurred, supports targeted frame and audio repair, and keeps observational evidence apart from causal inference.
  3. Design and Development: The four-layer governance model, its invariants and algorithms (Section 4), realized in two coupled open-source artifacts, Agentic Work Lab and PublishOps CrossCast (Section 5).
  4. Field Demonstration: Use of the artifacts from 26 October to 3 November 2026 in one creator–engineering laboratory, spanning two episodic series (GPT Duty Log Ep 01–06 and Whale Girl Shift Log Ep 01–07), standalone experimental studies and the cross-platform short film I Watched It For You (v3).
  5. Evaluation: Following FEDS (Venable et al., 2016), we combine naturalistic evaluation (a 69-record operational journal, a scheduled heartbeat trace, a five-platform release and a 55-record channel snapshot) with artificial evaluation through offline regression tests (2,737 test functions in CrossCast at commit 75b7abc, many of which simulate faults, and 10 workflow gate tests in Agentic Work Lab) (Section 6).
  6. Communication: Publication of source code, SHA-256-recorded media deliverables (N = 30 versions, 2.21 GB), machine-readable JSON/CSV receipts and a script that recomputes every reported figure (paper/reproduce_paper_tables.mjs).

Researcher role. The author designed, operated and evaluated both artifacts. We therefore treat the study as researcher–practitioner intervention in the sense of action design research (Sein et al., 2011) and technical action research (Wieringa, 2014). Two choices limit the resulting bias: the evidence consists of machine-readable receipts written when each event happened rather than retrospective accounts, and every receipt, script and dataset is public so that each figure can be recomputed independently.

3.2 Epistemic Hygiene and Evidence Classification Protocol

A central methodological element of the study is an explicit epistemic hygiene protocol applied to all project documentation and data exports (Runeson & Höst, 2009). For every research topic and operational update, the laboratory records four elements: (i) the original claim, (ii) visible primary evidence, (iii) an independent verification test, and (iv) applicable limits. Specifically:

  • Separation of Observation and Causal Inference: Platform observations (lifetime views, 24-hour completion rates, command durations) are stored with sampling timestamps and provenance notes. Causal inferences, such as asserting that an AI editing technique increased recommendations, are rejected unless backed by controlled, age- and topic-matched comparisons.
  • Granular State Differentiation: Local preparation, dry-run rehearsal, sign-in preflight, submission, platform review and verified public visibility are distinct states. UI observations and API verifications occupy separate fields, and an unverified or timed-out read-back is recorded as UNKNOWN rather than coerced into success or failure.
  • Immutable Snapshot Preservation: Repeated data collections are archived as separate observations (for example, the 28 October afternoon snapshot of 52 records is kept apart from the evening snapshot of 55 records and from the daily updates of 29 October–3 November) rather than overwritten.
  • Explicit Tagging of Unexecuted Plans: Planned designs (such as a blinded identical-task comparison of models on merchant research) and unmeasured optimizations (such as the wall-clock gain of concurrent publication) stay labelled as unrun until live receipts exist.

3.3 Data Sources and Evidence Window

The evaluation draws on records with different sampling windows, which we keep separate: the operational journal (69 records; 46 timestamped between 26 October 01:27 and 27 October 02:45, UTC+8; exported on 28 October); the scheduled heartbeat trace (28 October); the channel snapshot (55 records sampled on 28 October at 21:04, UTC+8); the release record of I Watched It For You (v3) (2–3 November); the media manifest (30 versions, GitHub assets checked on 3 November); and the CrossCast code at commit 75b7abc (3 November). 4.2 Layer 1: Deterministic Sole-Operator and Temporal Scheduling Gate

To prevent race conditions and unauthorized autonomous execution during scheduled heartbeats, Layer 1 enforces a pure offline decision function Gplan before any network or platform adapter is invoked. As formalized in Algorithm 1, planRun is a side-effect-free admission filter. It first checks that the reference clock parses to a finite epoch value (lines 1–2), then applies three ordered circuit breakers: executor ownership (line 3), the stop flag (line 4) and the running lock (line 5). Only when all three pass does it scan the candidate jobs, rejecting missing or repeated identifiers (lines 6–9) and skipping jobs that are completed or lack explicit human authorization (line 10). Even when due jobs exist, it returns plan_only rather than acting, leaving content checks and confirmation to the later layers. Two properties of the implementation (scripts/operations-gate.mjs) matter for interpretation. A non-finite due time raises an error only for jobs that are authorized and not completed, because other jobs are skipped before their due time is parsed. And planRun is advisory: it returns a decision but cannot stop an agent that never calls it. In the laboratory the operations checklist requires the call; enforcement at the platform boundary comes from Layers 2 and 3, which sit inside the release command itself.

4.3 Layer 2: Plan-Hash Binding and Artifact Verification

Between plan approval and execution, an agent or background process may change a video export, swap a cover or alter platform copy after the project manager has reviewed the preview. Large deliverables (2.6 MB to 285.9 MB in our archive) can also be written incompletely or misread; the release record of the v3 film notes one earlier local read discrepancy that remains unexplained. Layer 2 closes this time-of-check-to-time-of-use gap with two invariants:

Governance Invariant 1 (Media Integrity): Let M = {m1, …, mK} be the release manifest, where each entry mi = (fnamei, Bi, Hi) gives a file name, an exact byte length Bi and an expected SHA-256 digest Hi. An artifact fi passes the delivery check iff basename(fnamei) = fnamei ∧ size(fi) = Bi ∧ SHA256(fi) = Hi. Decode and frame checks are recorded separately in production receipts.
Governance Invariant 2 (Plan-Hash Confirmation Binding): Before any platform write through vpub publish, the release plan P—target platforms, account identities, video and cover SHA-256 digests, aspect ratio, visibility and platform copy—is serialized as JSON with sorted keys and compact separators and hashed, H(P) = SHA256(CanonicalJSON(P)). Execution is refused unless the command supplies --confirm Huser with Huser = H(P); a changed plan has a new digest, so a stale code is refused.

Both check-delivery.mjs (Node.js) and vpub (Python) hash media in streamed chunks rather than loading whole files, and the delivery check rejects manifest names that are not plain file names. The manifest records a zero-error full decode for five of the 30 deliveries (entries 26–30); update notes record decode checks for several others. The plan digest also names the receipt file—one per plan and platform—so a second attempt at the same plan finds the first attempt's receipt instead of starting afresh (Section 4.4). Invariant 2 binds the command to the exact content that was reviewed; it does not authenticate who approved it. The CLI records --person-approved as the caller's attestation and states that it cannot verify who supplied it, so human authority rests on procedure (the agent must stop and show the plan) while the digest guarantees that what runs is what was shown. 4.4 Layer 3: Idempotent Receipt State Machine and UNKNOWN-State Suppression

To answer RQ2, we model each browser publication attempt in PublishOps CrossCast as a durable receipt whose changes are written atomically under a file lock, while cross-process OS locks (process_lock.py) keep two runs from driving the same browser profile (Figure 2, Algorithm 2). The receipt is stored at a path named by the plan digest and the platform and holds Rp = (key, acctp, Hmedia, Hmeta, fsubmit, σp, widp, τlog), where fsubmit is the implementation's final_submit_attempted field and σp its state. Before pressing, the receipt also records the account's existing work identifiers, so that read-back can later look for exactly one new work. 3:  path ← ReceiptPath(H(P), p)
4:  if Exists(path) ∧ ¬resume then abort attempt_exists  // never reset an attempt to upload again
5:  if resume ∧ Exists(path) then Rp ← Load(path); require same Hmedia and acctp, else abort receipt_conflict
6:  if resume ∧ ¬Exists(path) ∧ the publication record shows media selected or a press attempted then abort receipt_missing
7:  VerifySHA256(P.media, P.covers); select media; Rp.media_selected ← true; PersistAtomically(Rp)
8:  if Rp.fsubmit = true ∧ ¬PlatformShowsUnsubmittedDraft() then abort already_submitted
9:  Rp.σp ← UNKNOWN; Rp.fsubmit ← true; PersistAtomically(Rp)  // before the click
10: PressFinalSubmitOnce()  // a single Share / Post / Publish press
11: outcome ← AwaitConfirmationAndReadBack(acctp, new works not listed before the press)
12: if outcome holds exactly one matching new work then Rp.σp ← SUBMISSION_VERIFIED; Rp.widp ← outcome.work_id
13: else keep Rp.σp ∈ {UNKNOWN, SUBMITTED_UNVERIFIED}  // never re-press; escalate to vpub verify or a person
14: PersistAtomically(Rp);  ReleaseProcessLock(p, acctp);  return Rp
Proposition 1 (At-Most-Once Automated Final Submission). Assume (A1) every final submission for plan P on platform p goes through the receipt transaction of Algorithm 2; (A2) receipt writes are atomic and durable; and (A3) receipts are not edited by hand. Then automated runs issue at most one final press per (P, p), with one exception: (A4) a resumed run may press again when the platform shows that the earlier work is still an unsubmitted draft.
Proof sketch. The receipt is saved with σp = UNKNOWN and fsubmit = true before the press (line 9). A later run on the same plan either finds the receipt and stops (line 4) or resumes it, in which case line 8 refuses another press while fsubmit = true unless (A4) holds. If the receipt file has disappeared while the publication record shows a selected file or an attempted press, the run stops (line 6) instead of uploading again. ∎

Proposition 1 is a safety guarantee, not a liveness one. A crash between saving the receipt and pressing leaves an UNKNOWN receipt for a submission that never happened; the design accepts such false alarms because the opposite error, a duplicate public post, cannot be undone. Whether an UNKNOWN submission published is settled afterwards by vpub verify, which checks that the signed-in account is the receipt's account and upgrades the receipt only when it finds exactly one matching new work, or by a person whose confirmation is recorded beside the receipt without relabelling it. Resumable byte offsets belong to API routes (upload_resume.py in the laboratory's 0.15.1 snapshot); the browser route instead refuses to upload again once its record shows that a file was selected.

4.5 Layer 4: Identity-Bound In-Place Revision and Consent-Bound Deletion

Beyond first publication, channel operations revise captions and covers, assign chapters and occasionally delete test works. An agent that implements an edit as delete-and-repost, or deletes without confirming the target's identity, turns a reversible correction into an irreversible loss. Layer 4 binds every revision and deletion to the receipt's account and work identifier (Algorithm 3), developed across PRs #20, #21, #25, #29 and #30.

Algorithm 3: Identity-Bound In-Place Revision & Consent-Bound Single-Work Deletion (vpub edit & vpub delete)
Input: Receipt key K, patch ΔP or deletion request, mode ∈ {VERIFY_ONLY, APPLY_EDIT, DELETE_WORK}
Output: Edit or deletion state and audit entry
1:  Rp ← LoadReceipt(K); require the signed-in account = Rp.acctp (expected_identity)
2:  if mode ∈ {VERIFY_ONLY, APPLY_EDIT} then
3:     live ← ReadNativeEditorFields(Rp.widp)  // page translations and comments are ignored
4:     if live = ΔP.target then return EDIT_VERIFIED  // nothing to save
5:     if mode = VERIFY_ONLY then return EDIT_MISMATCH
6:     if the platform offers no in-place edit for this work then return EDIT_UNAVAILABLE  // never delete or repost instead
7:     checkpoint EDIT_PREPARING; ApplyInPlace(Rp.widp, ΔP)  // video bytes and visibility unchanged
8:     reopen the editor; return EDIT_VERIFIED if read-back equals ΔP.target, else EDIT_SUBMITTED_UNVERIFIED
9:  else if mode = DELETE_WORK then
10:    require a dry run and a person's approval of this exact work (--confirm code, --person-approved), stored durably
11:    wait until the deletion control is ready; DeleteSingleWork(Rp.widp)
12:    refresh the catalogue; report success only if the work is absent

Algorithm 3 adds three safeguards. First, every read or change begins by confirming that the active session belongs to the receipt's account (expected_identity), preventing cross-account changes. Second, an edit compares native editor fields rather than the rendered page, and where the platform offers no in-place edit—as for an X post whose menu has no Edit action—the run ends with EDIT_UNAVAILABLE and attempts no deletion, repost or reply: compensation by repost would lose the post's identifier, replies and reach (Section 2.4). Third, a deletion requires a dry run and a person's approval of that exact work, waits until the deletion control is ready (PR #30), and counts as done only when a refreshed catalogue no longer lists the work (PR #29).

7. Discussion

7.1 Theoretical Implications for Project Management and Human–AI Governance

The study adds to work on AI in project management (Holzmann et al., 2022; Müller et al., 2024; Raisch & Krakowski, 2021) in four ways.

  1. Stage gates become commit protocols when agents act. Prior multi-agent frameworks coordinate handoffs mainly through role prompts (Wu et al., 2024; Hong et al., 2024; Qian et al., 2024). In this case the controls that held were those moved out of prompts into code at the point of action: an admission function, a content digest that the command must present, and a receipt written before the irreversible step. Read through Section 2.4, a stage gate in agentic delivery is less a meeting than a commit protocol, with configuration management (Whyte et al., 2016) supplying its notion of identity.
  2. Automation authority is state-dependent. Levels-of-automation models treat autonomy as a design-time choice (Parasuraman et al., 2000; Shneiderman, 2020). Here autonomy changes with the receipt's state: agents act freely while nothing irreversible has happened and lose the authority to retry as soon as a final submission may have occurred.
  3. At-most-once moves work to people, and that work needs design. Choosing at-most-once over at-least-once converts possible duplicates into in-doubt cases that a person must resolve, which is Bainbridge's (1983) irony in a new setting: the human receives exactly the cases automation cannot settle. The Douyin case was closed with a phone screenshot; governance designs should budget for this work and give the person a read-back command and an evidence bundle rather than a bare alert.
  4. Epistemic governance is a project deliverable. Provenance fields, SHA-256 manifests and non-causal labels in exported summaries made it possible to report what happened without claiming more. Where AI adoption is often reported through gains that cannot be checked, this reporting discipline is itself part of governance.

7.2 Answers to the Research Questions

  • RQ1 (governance architecture and handoff control). Stage-gate principles can be expressed as four software-enforced layers whose decisions are deterministic and testable (Section 4). Evidence: the gate's decision function and its ten passing tests, four automation-triggered records and one audited heartbeat without writes, and a journal recording one write and no replay (Table 3). Limit: the journal records outcomes, so it cannot show blocked attempts, and planRun binds only agents that call it.
  • RQ2 (idempotent release engineering and recovery). A receipt saved as UNKNOWN before a single final press yields at-most-once automated submission under assumptions A1–A4 (Proposition 1), with read-back or a person deciding the outcome. Evidence: the code path at 75b7abc, 2,737 offline test functions including fault paths, a private crash-recovery check that kept one YouTube video ID across two forced exits, and two Douyin read-back timeouts handled without re-submission or relabelling. Limit: few field instances, and safety is paid for with false in-doubt cases.
  • RQ3 (empirical characteristics and boundaries). Local governance checks were small next to platform waiting: in one Instagram run, pre-publication checks took 11.019 s and the wait after Share 380.551 s (92.32% of the publish command). Quality checks caught frame and audio defects (Table 8), and the reporting protocol kept non-comparable cohorts apart (Table 10). Limit: single observations from one laboratory over nine days (Section 7.4).

7.3 Managerial and Engineering Lessons Learned

  • Measure the Wait Before Optimizing Concurrency: In the one instrumented run, local governance checks took 11.019 s and the wait after Share 380.551 s (Table 7). Speeding up local steps would change little; safe session isolation and bounded concurrency (Figure 4) are the more promising levers, although their gain has not yet been measured.
  • Design Editable Intermediate Representations: Decomposing deliverables into code-driven timelines, separate audio tracks and structured JSON patches lets project managers enforce targeted revisions (Table 8) without discarding validated upstream work.
  • Preserve Original State on Verification Interruptions: When platform security challenges or missing edit permissions occur, tools should never delete, repost or overwrite existing works automatically, and a human confirmation should be recorded beside the receipt rather than overwriting it.
  • Budget for In-Doubt Resolution: An at-most-once design produces cases that only a person can close; give that person a read-back command and the evidence, and track how long such cases stay open.

7.4 Threats to Validity and Limitations

Following case-study guidance for software engineering (Runeson & Höst, 2009), we report the boundaries of the evidence.

  • Internal validity. The Instagram timing (412.217 s) and the heartbeat (31.175 s) are single instrumented observations, and client-side timing cannot separate transfer, processing and confirmation within the 380.551 s wait. The operational journal is a selected-fields export: 31 of its 69 records carry no event or state name, nine are silent on writes, and it records outcomes rather than refused attempts. An earlier local read discrepancy on the film's file remains unexplained; later reads matched, which does not show that its cause was removed.
  • Researcher role. The author built, operated and evaluated the artifacts. We limit the risk of motivated reporting by relying on receipts written when each event happened, publishing all data and code, and recomputing every figure with a script; the study nonetheless remains a single-researcher intervention (Sein et al., 2011; Wieringa, 2014).
  • Construct validity. Suppression of writes is not directly measurable from outcome logs (Section 6.1). Model names denote workflow roles, not authenticated model versions. Test-function counts measure the volume of checking, not coverage. Plan-hash confirmation binds content, while human approval is attested by the caller. The blinded identical-task comparison of GPT and DeepSeek (docs/model-workflow_EN.md) has not been run, so no claim is made about relative model capability, speed or cost.
  • External validity. Evidence comes from one laboratory, one account per platform and a nine-day window, with TikTok suspended after a sign-in with a Hong Kong (+852) number failed. Platforms differ structurally—browser versus API routes, and human confirmation on Douyin—so the latency figures do not transfer. What we expect to transfer is the mechanism: any agent that submits to an endpoint without server-side idempotency keys faces the same retry dilemma. Generalization is therefore analytical, by architectural similarity, rather than statistical (Flyvbjerg, 2006; Wieringa & Daneva, 2015).
  • Reliability. The repositories have changed since the snapshot (later CrossCast pull requests add tests, for example); all figures refer to the files and commits named in Section 3.3. Line counts are physical lines, and the descriptive statistics use sample standard deviations and linear quartiles.

8. Conclusion and Future Work

This Design Science study asked how to govern human–AI collaborative delivery when agents act on external platforms that cannot undo or de-duplicate their actions. Agentic Work Lab and PublishOps CrossCast combine clear role boundaries between a human project manager and three AI workflows (GPT/Codex, Claude and DeepSeek) with four layers: an owner, stop-flag and due-time gate; plan-hash binding with SHA-256 media checks; a receipt state machine that saves an UNKNOWN state before a single final submission and never re-submits automatically; and independent read-back with human escalation. Over nine days, the field records show one recorded platform write and no recorded replay in a 69-record journal, an in-doubt Douyin submission held without re-submission, 30 SHA-256-recorded video versions, and a five-platform release whose evidence is kept per platform; 2,737 offline test functions exercise the corresponding code at commit 75b7abc. These results support the mechanisms' design intent within the limits of a single case.

Future work follows from those limits: (1) record gate decisions and refused attempts, not only outcomes, so that suppression becomes measurable; (2) time bounded concurrent publication against sequential runs; (3) run the planned blinded identical-task comparison of models with logged costs; and (4) replicate the framework with other teams and accounts.
