摘要（Abstract 完整中文对照）

背景（Context）： 随着大语言模型（LLM）智能体在数字工程与媒体生产项目中从“对话式助手”演进为“自主执行主体”，项目管理面临着严峻的治理空白。多智能体工作流频繁遭遇角色交接失调、非幂等的外部副作用（例如网络超时后触发的跨平台重复发布）、静默质量退化以及混淆的绩效归因。

目标（Objective）： 基于设计科学研究（Design Science Research, DSR）范式与阶段门控（Stage-Gate）项目控制理论，本研究设计、实现并实证评估了一套面向多智能体、多平台数字交付的可审计“人在回路（HITL）”项目治理框架与发布运维系统（Agentic Work Lab 与 PublishOps CrossCast）。

方法（Method）： 我们形式化提出了四层治理架构：（1）确定性的单人主控与时间窗口调度门（planRun）；（2）耦合流式 SHA-256 媒体完整性校验的加密计划哈希锁（--confirm CURRENT_PLAN_HASH）；（3）在异构 API 与浏览器自动化端点上将不确定提交结果锁定为 UNKNOWN 态以抑制自动重试故障的幂等回执状态机；以及（4）独立回读校验与人工异常接管协议。我们利用纵向真实项目制品对该框架进行了实证评估，涵盖 N = 69 条脱敏运维事件日志、N = 55 条频道发布快照记录、N = 30 个经加密校验的视频交付版本（总计 2.21 GB），以及跨 126 个测试模块的 2,737 个自动化验证测试用例。

结果（Results）： 在涉及多智能体协作（人类项目管理下的 GPT/Codex、Claude 与 DeepSeek）的 69 个运维检查点中，治理门在 68 个非写入窗口中成功抑制了未授权变更，仅在授权窗口执行 1 次真实写入（0 次重复上传重放，0 起新增风险事件）。经核实的自主巡检运行表现出 24.992 秒 的触发延迟与 31.175 秒 的执行耗时，任务错误率为零。跨 5 大平台（Bilibili、YouTube、X、抖音、Instagram）的发布评估证实，在抖音出现程序化回读超时期间，将状态锁定为 UNKNOWN 成功阻止了重复发布并完整保留了审计轨迹。Instagram 端到端发布（总耗时 423.236 秒，发布命令耗时 412.217 秒）的阶段级延迟拆解表明，92.32%（380.551 秒） 的命令耗时集中在“提交后的平台确认等待期”，从而精准定位了非幂等智能体重试的核心脆弱窗口。

结论（Conclusions）： 代理式（Agentic）工作流的有效项目管理，必须从“提示词层面的软性规劝”转向“确定性的阶段门控不变式、加密制品锁定与幂等状态机恢复”。全部源代码、数据模式与脱敏实证数据集均已公开归档，为多智能体项目治理建立了可复现的基准。

第 1 节：引言与三大研究问题（Section 1: Introduction & RQs）

论文第一部分指出，将多个异构大模型（GPT/Codex、Claude、DeepSeek）投入真实生产环境时，传统项目管理无法应对三大故障模式：

  1. 多智能体交接漂移与角色模糊（Multi-Agent Handoff Drift）： 异步智能体缺少形式化所有权锁，容易覆盖人工审核结果或在非授权时段写文件。
  2. 不确定状态下的非幂等外部副作用（Non-Idempotent External Side Effects）： 社交平台发布兼具官方 API 与浏览器自动化（Playwright）。网络抖动、审核队列或回读超时会让提交处于不确定态（UNKNOWN），传统智能体盲目自动重试会导致严重重复发帖。
  3. 绩效评估中的认知混杂（Epistemic Confounding）： 把累积了长周期流量的老视频与刚上线的新 AI 视频混在一起比均值，会产生严重的曝光时间混杂偏差。

为此，论文提出 3 个核心研究问题（RQs）：

  • RQ1（治理架构）： 如何将阶段门控项目管理原则形式化为确定性的软件不变式，以治理多模型交接并杜绝未授权或重复的自主操作？
  • RQ2（容错发布工程）： 当提交后验证遇到超时或人工认证障碍时，幂等回执状态机如何协调混合 API 与浏览器通道的跨平台数字发布？
  • RQ3（实证与认知验证）： 将该治理架构部署于纵向多平台生产工作流时，表现出怎样的实证运行特征、延迟瓶颈与方法学边界？

第 2–3 节：理论背景与设计科学研究方法（Sections 2 & 3）

第 2 节综述了阶段门控理论（Cooper, 1990；Bianchi et al., 2022）、人机协同控制（Raisch & Krakowski, 2021；Shneiderman, 2020）、多智能体框架对比（AutoGen、MetaGPT、ChatDev，对应 Table 1）以及幂等状态机理论（Schneider, 1990；Kleppmann, 2017）。

第 3 节定义了设计科学研究（DSR）六步法与 4 条强制学术诚实准则（Epistemic Hygiene Rules）：① 观测与推断严格分离；② 状态颗粒度显式区分（绝不把超时未确认当成失败或成功，必须锁入 UNKNOWN）；③ 历史快照不可变追加；④ 未执行实验显式标注。

第 4 节：四层人机协同治理架构、三大数学公式与三大核心算法（Section 4）

核心数学公式 1（Layer 1 纯函数调度门控谓词，对应定理 A.1）：
G_run(C, E, S_chk, t_now) = I_enabled(C) ∧ I_window(t_now, W) ∧ I_cooldown(t_now, E, Δt_min) ∧ I_checklist(S_chk)
含义： 只有当配置开关开启、当前时间处于授权窗口 W 内、距离上次运行已满最小冷却时间 Δt_min、且任务清单存在未认领的就绪项时，门控谓词才返回 1（放行），否则一律返回 0（硬拦截）。
核心数学公式 2（Layer 2 流式 SHA-256 载荷与计划哈希锁，对应定理 A.3）：
H_plan = SHA256(Canon(M, T, H(f)))，执行条件：I_exec(τ_user, H_plan) = 1 ⇔ (τ_user == H_plan)
含义： 将规范化后的元数据 M、目标平台列表 T 以及 64-KB 分块流式计算的媒体文件 SHA-256 哈希 H(f) 组合生成唯一计划指纹 H_plan。执行发布时，用户或上层门控传入的确认令牌 τ_user 必须与当前重算的 H_plan 完全一致，哪怕改动 1 个字节也会立即中止执行。
核心数学公式 3（Layer 3 幂等状态机“最多发布一次”安全不变式，对应定理 A.2）：
∀ p ∈ T, Σ_{k=1..K} I(transmit(f, M, p, k)) ≤ 1
含义： 对于任何目标平台 p，在任意 K ≥ 1 轮恢复与核对过程中，一旦首次尝试进入 SUBMITTING 状态，后续任何因回读超时进入 UNKNOWN 态的恢复操作都只允许调用只读查询接口（verify_remote_state），绝不再次调用字节流上传接口（transmit），从而在数学上严格保证外部平台最多只会被写入 1 次。

三大形式化算法（Algorithms 1–3）一览：

  • Algorithm 1 (planRun)： 确定性时间窗口与清单门控算法（纯函数，无外部 I/O 副作用，复杂度 O(|E| + |S_chk|)）。
  • Algorithm 2 (executePublishStep)： 跨平台幂等回执状态机与 UNKNOWN 锁定算法（涵盖 8 个状态：INIT, DRY_RUN, PREFLIGHT, SUBMITTING, VERIFYING, PUBLISHED, UNKNOWN, NEEDS_HUMAN, FAILED）。
  • Algorithm 3 (auditCohortComparison)： 频道作品序列非参数分层与认知混杂审计门算法（自动计算 Mann–Whitney U 统计量、p 值与秩双列相关系数 r_rb，拦截混杂归因）。

第 6–7 节：讨论、有效性威胁与结论（Sections 6 & 7）

  • 理论贡献： 将项目管理中的“阶段门控（Stage-Gate）”从人工会议评审推进为“确定性软件不变式 + 加密哈希锁 + 幂等回执状态机”。
  • 实践启示： 揭示了混合自动化发布中 92.32% 的耗时集中在提交后等待确认期 这一关键工程定律，确立了“超时锁入 UNKNOWN 态、严禁盲目自动重传”的行业准则。
  • 四维有效性威胁防御（Threats to Validity）： 全面覆盖构造有效性（Construct Validity）、内部有效性（Internal Validity）、外部有效性（External Validity）与结论有效性（Conclusion Validity）。
